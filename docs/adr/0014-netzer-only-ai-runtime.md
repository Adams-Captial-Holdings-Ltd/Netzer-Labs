# ADR 0014 — Netzer is the only AI runtime; Paperclip runners are disabled and fail closed

**Status:** Accepted (owner-approved plan, 2026-09-26; recorded 2026-09-29; amended by decisions 32, 33 and 35). Plan number 0013; repo number 0014 — [why](../features/paperclip/decision-log.md#adr-numbers).

## Context

Paperclip can run agents itself: its native runner, local adapters and remote profiles. Any of them would be a second, ungoverned AI runtime beside Netzer's, which owns the guardrail, cost ledger, audit and tool policy. The plan names the risk as a data leak ([minimum sellable product](../features/paperclip/minimum-sellable-product.md), B3).

`enableNativeRunner` defaults to true and is settable (VERIFIED, `pc:validators/instance.ts:44` @LATEST), so a re-pin or a settings change can switch a runner on silently. The risk register rates "native runner re-enabled by re-pin" High.

## Decision

1. **`runAgentTurn` is the only AI runtime.** Paperclip's native runner, local adapters and remote profiles are off. Pack agents are http-adapter agents that dispatch to Netzer ([ADR 0013](0013-sync-attach-execution-contract.md)); there are no non-http agents.
2. **Fail-closed runtime lock (decision 32).** The Paperclip task's environment locks what can be locked: hidden settings for adapters, plugins and the feedback preference, an http-only adapter list, and telemetry off. The native-runner flag is deliberately not hidden (decision 35): it defaults on in a fresh database and a hidden setting refuses any change, so the operator bootstrap turns it off and the orchestrator reads it. At start and every 60 s the orchestrator reads the five conditions live in the deployment's one company (decision 15; a second company would be invisible to the auditor), through one read-only company-member board key, the **lock auditor** (secret field `lock_auditor_key`; never an agent key, never an instance-admin key): `enableNativeRunner` is off, no agent uses a non-http adapter, no remote profile exists, no tool application or connection exists, and no agent has a timer heartbeat; the health route also lists `instance.adapters` and `instance.plugins` as hidden. There are three outcomes. **Clean** opens the Paperclip surface. **Violated** at start means the orchestrator will refuse to start, so the ECS circuit breaker fails the deploy. **Unknown** (Paperclip unreachable, the key missing or rejected, a response whose shape drifted) lets the process start but closes a latch on the Paperclip surface, which stays closed with a real non-2xx until a later read is clean. The Paperclip client, the reconciler and the private dispatch route all read the latch. A violated check never warns and continues, and an unreadable one fails closed. The lock is enforced while Paperclip routing is on (`CCE_PAPERCLIP_ENABLED`, the routing switch; agents are armed separately by the runtime-config key `paperclip/enabled_agents`); with the flag off it does not run, the reconciler stays read-only (default shadow mode) and dispatch stays inert until agents are armed, so turn the flag on before arming agents or leaving shadow mode (whether it should run whenever Paperclip is configured, whatever the flag says, is an open owner question). A verdict that has not been refreshed for five minutes, for example because a read never settles, closes the latch as `unknown:lock_check_stale`.
3. **Private dispatch.** The dispatch route is served only by a second listener on a private port (3001) that only Paperclip's security group can reach; the public app answers 404 for it in code, because a peer-IP check would fail open behind the tunnel. The allowlist `PAPERCLIP_HTTP_ADAPTER_PRIVATE_ENDPOINT_ALLOWLIST` names that origin, which is what lets Paperclip's http adapter reach a private address at all (upstream's guard refuses private addresses that are not listed and always refuses link-local metadata targets, but it allows public endpoints by default, so the setting is not an egress restriction). The orchestrator's own Paperclip address from runtime config must be private (loopback, RFC 1918 or `.internal`) and is never followed through a redirect. The bearer is rotated at install and never logged (pino redacts the known secret field names at the top level and one level down; it does not scan content). Paperclip telemetry is off (`PAPERCLIP_TELEMETRY_DISABLED=1`, `DO_NOT_TRACK=1`, `PAPERCLIP_ANNOUNCEMENTS_ENABLED=false`).
4. The lock is contract-tested at every digest ([ADR 0019](0019-paperclip-compatibility-program.md)), live, with `npm run test:paperclip:contract`. The script exits green with zero tests when `PAPERCLIP_TEST_AUTH_SECRET` is unset, so read the passed-test count and not only the exit code (step 2 handoff, A125).
5. **No cleanup code (decision 33).** The lock fails on any non-http agent, so a Paperclip that already holds built-in agents (the existing staging one) makes the orchestrator refuse to start with a clear code. How such an instance is cleaned is the owner's call; the bootstrap never deletes an agent or a user.

## Consequences

Good: one runtime means one place for guardrails, cost and audit, and a re-pin cannot quietly add a second one.

Bad:

- No Paperclip feature that executes agents is available to packs.
- Every digest bump must re-prove the lock, and a red check blocks the deploy.
- Residuals: tool gateways are not read at start; a violation that appears while running is caught within 60 s, not instantly; `company.import` is not floored (pack install may use it, and the adapter allowlist alone may not stop it); the native-runner flag has no prevention, only detection; until the bootstrap has made the auditor the verdict is unknown and the surface stays closed.
- Residuals found in the step-2 review: the lock reads an http agent's adapter type, not where it points, so an http agent aimed at another reachable address is not caught; the viewer-role auditor key reads full agent rows, which hold the dispatch bearer, so the key is as sensitive as the bearer; a violation read at start refuses every start of the orchestrator (a deploy, a scale-out, a crash restart), so one Paperclip toggle can become an outage until it is reverted; the lock follows `CCE_PAPERCLIP_ENABLED` (decision 2); an agent row with no `runtimeConfig` reads as heartbeats off, and a draft tool connection created by another user is invisible to the auditor until it leaves draft; the lock audits the Paperclip address from runtime config at each read, while clients built earlier keep the address they were built with.
- The auditor key is rotated by hand: clear `lock_auditor_key` to `REPLACE_ME` in the Paperclip secret, run the bootstrap (it creates a new auditor and a new key), then **roll the orchestrator service** with a new deployment. ECS reads secrets only at task start, so a running task keeps the old value and its lock stays closed until it is replaced. Rotation does not revoke the old key: Paperclip board keys carry no expiry and the bootstrap makes no revoke call, so an operator removes the old auditor's board key and membership in Paperclip after the roll. A failed secret write after the auditor was created leaves the same kind of orphan.

- **Reversibility:** two-way. The lock is settings plus checks.
- **Revisit trigger:** a digest bump changes the default or meaning of any locked setting (the contract suite goes red), makes any of the auditor's reads admin-only, or adds an env default for the native-runner flag (then hide it too); or the first staging deploy shows a false `violated`.

## Alternatives considered

- **Paperclip's native runner for some agents.** Rejected: a second AI runtime ([DO NOT BUILD](../features/paperclip/do-not-build.md)).
- **Local adapters or remote profiles.** Rejected for the same reason.
