# ADR 0013 — SYNC_ATTACH execution contract and the deterministic-writes rule

**Status:** Accepted (owner-approved plan, 2026-09-26; recorded 2026-09-29; touched by decisions 18, 30, 36 and 38). Built in step 4 on the branch `feature/wp-step4-execution-contract`; not merged or deployed. The deterministic-writes part was built in step 5 on `feature/wp-step5-safe-actions`; not merged or deployed. Plan number 0012; repo number 0013 — [why](../features/paperclip/decision-log.md#adr-numbers).

## Context

Today Paperclip marks a run "succeeded" the moment Netzer answers its dispatch, which causes duplicate AI work (VERIFIED in source). Two blockers cannot be manual ([minimum sellable product](../features/paperclip/minimum-sellable-product.md), section A): correct execution semantics, and retry-safe business actions. An AI retry must never create a second EHR record or a second calendar booking.

Jev first chose NATIVE_ASYNC_MONITOR (1.0), then **revised to SYNC_ATTACH (1.0)** after the owner made true run states a blocker.

What Paperclip does, read at the plan and then MEASURED at v2026.916.1 in a sealed local container (2026-10-03, spike A120): the http adapter never reads the response body; a non-2xx answer marks the run failed and the issue blocked, and Paperclip never sends that dispatch again. A retry gets a new run id plus `context.retryOfRunId`. One issue has one run at a time. A `done` written before the 2xx causes no follow-up run, and a comment-only write makes Paperclip run the job a second time. A late write with the ended run id is accepted. Where the plan-time source read and the measurement differ (for example, a failed run is not re-sent), the measurement wins; it is re-measured at every digest bump.

What Netzer did before step 4 (checked at 29309c8): `tryClaimOnce` had neither a renewable lease nor a fencing token and recorded no holder; the dispatch route answered 202 `agent_not_enabled` and 503 `paperclip_disabled`, which forged outcomes; shutdown force-exited after 28 s.

## Decision

**SYNC_ATTACH.** Dispatch is held open for one execution attempt.

- **Outcome.** 2xx comes back only after the outcome is written to Paperclip with the run id of a dispatch that is attached at that moment. Failure returns non-2xx with an `error` code (Paperclip never reads the body; it is for logs and tests):

  | Code | Status | When |
  |---|---|---|
  | `cost_cap` | 402 | the cost cap is reached |
  | `model_access` | 503 | the kill switch is on, or Bedrock access or availability failed |
  | `connector_auth` | 502 | Paperclip refused our credential or run |
  | `agent_failed` | 500 | any other failure of the turn |
  | `attempt_in_progress` | 409 | a genuine new wake while an attempt runs |
  | `attempt_timeout` | 504 | the hold cap passed |
  | `lease_lost` | 409 | this holder was fenced out |
  | `delivery_failed` | 502 | the completion write failed in a way that proves it was not applied; the outcome is kept |
  | `delivery_unknown` | 500 | the completion write got no answer, or its lease expired mid-write; never retried blind |
  | `agent_blocked` | 409 | a guardrail blocked the turn; the notice was delivered as a comment |
  | `draining` | 503 | SIGTERM was received |
  | `attempt_store_unavailable` | 503 | the attempt row could not be read or written |
  | `agent_not_enabled` | 409 | the agent is not armed |
  | `effect_unknown` | 409 | a deterministic write's outcome is not known; a person must run `pack effect resolve` |
  | `effect_conflict` | 409 | the same effect key arrived with a different payload |
  | `effect_retry` | 503 | a write was provably not sent, or the task is draining; safe to retry |

  The route checks the bearer secret first (401), then the runtime lock (503 `paperclip_locked`), then draining. The 202 `agent_not_enabled` reply, the 503 `paperclip_disabled` reply and the kill-switch pre-check are removed.
- **Attempt identity** is one attempt row per issue: `PK = ATTEMPT#<issueId>` in the existing queue-lease table (no new table). It holds `attemptNo`, `state` (`running`, `recorded`, `delivering`, `delivered` or `failed`), a fencing `leaseToken`, the `holderId`, the lease expiry, the run ids that started or attached to it (at most 20), the recorded outcome and a `version` used for compare-and-set. A dispatch belongs to the attempt when its run id or its `context.retryOfRunId` is on the row. This REPLACES the earlier wording `(issueId, wake cause/revision)`: the measured Paperclip context carries no revision, so the retry link is the key. A dispatch that belongs attaches to the running attempt or gets its recorded result; any other dispatch is a genuine new wake and starts the next attempt (or answers 409 `attempt_in_progress` while one runs).
- **Leases** are renewable and fenced. The lease is 30 s, renewed every 10 s. Every holder write checks the attempt number, the token and the holder, then compare-and-sets on `version`; a stale holder writes nothing and its request ends 409 `lease_lost`. A store error fails closed (503 `attempt_store_unavailable`): running without the row would break "one execution". A task that finds an expired lease takes the attempt over with the token plus one.
- **Hold cap.** `ATTEMPT_HOLD_MS` is 240 s per request. If the attempt still runs then, the request ends 504 `attempt_timeout`; the holder keeps working and delivers the outcome late. The agent's adapter `timeoutMs` is 270 000 (it was 10 000).
- **Completion writer.** The outcome is recorded on the row before any delivery is tried. Delivery is one call with `X-Paperclip-Run-Id` set to the newest attached run id: `PATCH /api/issues/:id { status: "done", comment }` for a normal reply. A guardrail-blocked turn posts the notice as a comment and the attempt ends 409 `agent_blocked`, so Paperclip marks the run failed and the issue blocked; Netzer does not set the status, because a bare `blocked` or `in_review` PATCH is rejected 422 by Paperclip at this pin. The 2xx is written only after the row says `delivered`.
- **`pending_dispatch` sweep.** Every 5 minutes, under one runner lease, the sweep delivers each recorded outcome older than 60 s, ends an in-flight write whose lease expired as `delivery_unknown`, and writes one error log when an outcome stays undelivered for 15 minutes. Paperclip does not re-send a failed dispatch (measured), so the sweep is what delivers an outcome whose request is gone.
- **Failure handling inside an attempt (review fixes, step 4).** A waiting request that finds the lease expired re-runs the decision once (takeover, or `delivery_unknown` for an in-flight write) instead of polling a dead holder to the cap. A fenced renewal, or 25 s with no successful renewal, aborts the agent turn through its abort signal, so a store outage longer than the lease cannot leave two turns running; the delivery phase is never aborted. One store error at `record`, `markDelivered` or `releaseDelivery` is retried (3 tries); bookkeeping that still fails after the write was applied is logged as delivered-but-unrecorded and never re-delivered. A completion write the client provably never sent (lock closed, switch on, breaker open, or the client could not be built) carries `notSent` and ends `delivery_failed`, so the outcome is kept and the sweep retries it; an error from a request that may have gone out stays `delivery_unknown`. Identifiers are capped at 128 characters and the body at 64 KiB (413 `body_too_large`), both after the bearer check. Errors are logged by name where they happen, never by message.
- **SIGTERM.** The route answers 503 `draining` first (new starts and attaches); attempts this task holds keep running, and shutdown waits for them (an in-flight count) before it closes the servers, bounded by the 28 s backstop, which logs how many were still in flight. While a task holds an attempt it sets ECS task scale-in protection (`ecs:UpdateTaskProtection`), and clears it when the last attempt ends. A failed protection call is a warning, never a failed attempt.
- **Held-request limit and the fixed address (decisions 30, 34 and 38).** Step-2 spike (a) measured it on 2026-09-30: at v2026.916.1 a dispatch to a hostname is cut at 30 s, and one to a raw private IP at about 302 s; raw-IP holds of 240 s and 280 s succeed. So the dispatch goes to a raw private IP and attempts are capped at 240 s; longer work continues through a new wake. The fixed address is an internal Network Load Balancer in front of the orchestrator's private port 3001 (decision 38). Its first private IP is looked up at deploy time and added to Paperclip's adapter allowlist next to the interim DNS origin (decision 34), and the bootstrap script is given it as the dispatch URL. The load balancer's default 350 s TCP idle timeout is relied on (it is above the 240 s hold). The single looked-up IP sits in one zone; if that zone fails, the operator re-points it (accepted). There is no Paperclip patch. If a digest we must take closes the raw-IP path, the named fallback is a two-line `responseTimeoutMs` patch on the http adapter: an ADR 0019 last resort, with an upstream issue.
- **Waits and pauses.** As built in step 4, the only wait is a guardrail-blocked turn: its notice is posted as a comment and the attempt ends 409 `agent_blocked` (Netzer does not set the status; Paperclip rejects a bare `blocked` or `in_review` PATCH at this pin). Ending an attempt as `in_review` with a durable wait path is the plan's design for the review step (step 6) and is not built here. An agent's reply text is held in the attempt row until it is delivered (and for the row's 7-day TTL if the attempt fails). Pause is done by disabling routines and agents, never by 202 or 503 replies, which would forge outcomes; those replies are removed.

**Deterministic writes only.** Business writes happen only in deterministic L1 steps. AI (L2) steps read, analyze, recommend and draft. (L1 tool action: deterministic, idempotent, effect ledger. L2 agent task: LLM, no writes. L3 workflow: a Paperclip pipeline whose stages spawn L1 and L2 issues and whose review stages wait on humans.)

The bullets below say what step 5 built. The executor and the ledger are a library in this step; the Consequences section says what is not wired.

- **Effect ledger (as built in step 5).** The key is `(caseKey, stage, step, stageEntryNo)`, using the ingest `caseKey`. It survives Request Changes rounds and database restores. A retry returns the recorded result. The code is `src/lib/work/effect-ledger.ts` (types and key rules), `effect-rows-dynamo.ts` (the table) and `executor.ts`.
  - **Table.** The table is `effect-ledger` (`<app>-effect-ledger`, env `TABLE_EFFECT_LEDGER`). It has point-in-time recovery, a customer-managed key and a retain policy, like every table. It has no expiry (no `timeToLiveAttribute`), and no `ttl` attribute is ever written. The task role is granted the table and its index.
  - **Frozen key (owner decision 2026-10-03, one-way).** `PK = CASE#<caseKey>` and `SK = EFFECT#<stage>#<step>#<stageEntryNo>`. A frozen draft is stored under `SK = DRAFT#<stage>#<step>#<stageEntryNo>` in the same table. Once a live pack runs, this key and table shape cannot change.
  - **Key rules.** `caseKey` is 1 to 256 characters with no control characters. `stage` and `step` match `^[a-z0-9][a-z0-9_-]{0,127}$`. `stageEntryNo` is a positive safe integer. Anything else throws `InvalidEffectKeyError` before any store call.
  - **States.** A row is `pending`, `applied`, `retryable` or `unknown`. The first call creates the row as `pending` with a conditional write, then runs `apply()`. When `apply()` returns, the row becomes `applied` with the recorded result. When `apply()` throws an error with `notSent === true`, the row becomes `retryable` and the call throws `EffectRetryableError`. When `apply()` throws any other error, the row becomes `unknown` and the call throws `EffectUnknownError`. The next call on a `retryable` row moves it back to `pending` and runs `apply()` again. An `unknown` row stops every call with `EffectUnknownError`. A stored row whose state the code does not know also stops the call as `EffectUnknownError`, and nothing is written. Only `resolve` moves an `unknown` row: `applied` makes it `applied`, and `not_applied` makes it `retryable`. Every change is a compare-and-set on the row's `version`.
  - **Lost claim or lost record.** Before `apply()`, a call claims the row with a compare-and-set. If another holder won that compare-and-set, the call throws `EffectRetryableError` (`effect_retry`) and `apply()` is not run. After `apply()` returns, the call records `applied` with a compare-and-set. If another holder changed the row first, the call writes an error log line (IDs and hash only) and throws `EffectUnknownError` (`effect_unknown`). If the record call itself throws, the call writes the same kind of error log line and rethrows.
  - **Read before retry.** A call that finds a `pending` row (a holder that died, or a racing holder) never writes blind. `PENDING_SETTLE_MS` is 270 000 ms: the 240 s hold cap plus the 30 s lease. A `pending` row whose last update is younger than that is left alone, and the call throws `EffectRetryableError`, because an earlier holder's write may still be in flight and must not be repeated. After the window, if the caller supplied `readBack`, the call reads the outside world first. `{ applied: true, result }` records the row as `applied` (with the audit repair mark below) and returns the result. `{ applied: false }` claims the row and runs `apply()`. `'unknown'`, or a throw from `readBack`, makes the row `unknown`. With no `readBack`, the row becomes `unknown`. A `retryable` row has no settle window: it is claimed at once.
  - **Unknown index.** The sparse index `gsi1-unknown` lists the `unknown` rows. A row carries `GSI1PK = 'UNKNOWN'` and `GSI1SK = <updatedAt ISO>#<sha256 hex of "<PK>|<SK>">` only while it is `unknown`; the attributes are removed when the state changes. The hash keeps the sort key under DynamoDB's sort-key size limit, because a case key can be 256 characters. `pack effect list` reads this index. An index read is eventually consistent, so a row that just became `unknown` can take a moment to appear. All other reads of the table are consistent reads.
  - **Fencing.** `fence()` runs before every ledger write in `runEffect` and `saveDraftOnce`, and before `apply()`. It throws `FencedOutError` when the holder lost its lease, so a fenced-out holder writes nothing. `resolve` takes no fence.
  - **Draining.** While the task drains, a call that would write throws `EffectRetryableError` and writes nothing. A recorded `applied` result is still returned, and an `unknown` row still stops the call.
  - **Payload hash and conflict.** The payload hash is the sha256 of the payload as JSON, with object keys sorted by code unit. `undefined` hashes like `null`, and a `Date` hashes as its ISO string. A non-finite number, a bigint, a function, a symbol, a `Map`, a `Set`, any other non-plain object, a circular reference or an invalid `Date` is refused with `InvalidEffectPayloadError` before any store call. If a row exists and its hash differs, the call throws `EffectConflictError`. The check runs before the state is looked at, so it also applies to `applied` and `unknown` rows. The same key and the same hash returns the recorded result.
  - **Audit.** A row recorded as `applied` carries `auditPending: true` until the `effect_applied` audit row is written. The call writes the audit, then clears the mark with a compare-and-set. If the audit write fails, the call throws and the row stays `applied` with the mark. A later call on that row (a replay) sees the mark and writes the audit again, then returns the recorded result. If only clearing the mark fails, the error is swallowed and a replay writes the audit again. `effect_unknown` is written on a best-effort basis; a failed audit never hides the `EffectUnknownError`. `effect_resolved` carries the resolver as `userId`. `resolve` writes this audit row first and changes the row only after the audit write succeeds, so a failed audit leaves the row `unknown`. The details hold IDs and hashes only: `caseKey`, `stage`, `step`, `stageEntryNo`, `payloadHash`, `resultHash`, `issueId`, `runId`, `attemptNo`, `turnId`, and `outcome` on resolve. The payload, the result and error text are never written. All three actions are in the always-audited set.
  - **Frozen drafts.** `saveDraftOnce` saves a draft the first time and returns the saved text on every later call. It never runs `produce()` again once a draft exists. It refuses a draft over 300 000 bytes (UTF-8). It fences before the conditional create, and on a lost race it returns the stored text. Drafts write no audit row and never appear in the unknown list.
- **Paperclip writes** (transition, review, comment) are ledgered too, with read-before-retry, when they are made through the executor. The completion write on the dispatch path does not go through it yet (see Consequences).
- **Unknown outcomes** stop the work and never retry blind. An executor error that reaches the dispatch worker maps to `effect_unknown` (409, not retryable), `effect_conflict` (409, not retryable) or `effect_retry` (503, retryable) in `workFailure`. A person clears an unknown row with the CLI:
  - `pack effect list` prints one line per unknown row: `caseKey stage step stageEntryNo updatedAt` and the `issueId` when the row has one. With no rows it prints `No unknown effects`.
  - `pack effect resolve <caseKey> <stage> <step> <stageEntryNo> (--applied | --not-applied) --by <userId>` exits 0 and prints `Effect resolved`. A bad argument list prints the usage line and exits 2. `resolve` throws `EffectResolveError` with a `code`: `resolver_required` (a blank `--by`), `not_unknown` (the row is missing or not `unknown`) or `changed` (the row changed after it was read; the `effect_resolved` audit row was already written, and the row was not changed). `pack effect list` and `pack effect resolve` each print one line on any failure and exit 1: the error's name, plus `: <code>` for `EffectResolveError`. They never print the message, the stack or any payload. The CLI passes no result, so a row resolved with `--applied` hands an empty result to the next caller.
  - In a customer's AWS account, `effect resolve` decisions are the customer admin's (decision 18).

## Consequences

Good: run states are true, a duplicate dispatch executes once, and no AI retry can double-write.

Bad:

- Held-open dispatch across restarts is the top risk (High). Mitigation: attach semantics, lease takeover and live restart proofs (step 4).
- The internal load balancer adds about $16 to $20 a month per deployment.
- **Proved locally (step 4):** the attempt row, fencing, the held route, the completion writer, the sweep, drain and the CDK synth, by hermetic tests; and the Paperclip behavior in the Context, measured in a sealed local container.
- **PENDING on staging, not proved:** a restart or deploy mid-attempt and scale-in protection; the 45 s and 250 s holds through the load balancer; a Paperclip restart mid-attempt. These run at the staging trip, never in this repository's tests.
- **PENDING on staging, not proved (step 5):** the `effect-ledger` table exists after deploy and the task role can read and write it; a restart between `pending` and `applied` ends `unknown`, and `pack effect resolve` clears it against real DynamoDB; the joint restore drill includes the effect ledger. These run at the staging trip, never in this repository's tests. The restore drill belongs to step 13.
- **Proved locally (step 5):** the executor against an in-memory store, the DynamoDB row commands against a mocked client, the table's CDK synth (key schema, point-in-time recovery, no expiry, the sparse index, the task-role grant), the tool policy, the turn ID and per-call audit rows, and the `pack effect` commands, by hermetic tests. `npm run local:test:integration` was not run locally (port 4566 was in use); CI runs it.
- **The executor is a library in step 5; the completion write is not ledgered.** The completion write on the dispatch path (the agent's reply and the `done` status) still uses step 4's attempt row. It does not go through the effect ledger, because today's dispatch carries no case key and no stage (it carries `issueId`, `runId` and `retryOfRunId` only). The ledger key is frozen, so no stand-in key was invented. The write is wired when a later step (8 or 13) puts the case key and the stage on the wire. Until then, "Paperclip writes are ledgered" holds only for writes made through the executor.
- **Agent writes outside a run (A109, A119) are decided in step 5.** The two Paperclip write tools, `paperclip_add_comment` and `paperclip_create_subtask`, refuse before any Paperclip call when the turn holds no run. The refusal text points to the work screens. Humans act through their own keys (step 6) and the work screens (step 7). The tool policy that stops AI steps from writing is in the [security model](../security-model.md#ai-steps-cannot-write-step-5).
- Unknown-outcome writes stop for an operator instead of retrying (High); the effect ledger records them as `unknown`.
- A write whose holder died stays `effect_retry` for 270 s (`PENDING_SETTLE_MS`) before the read-back is trusted. This costs a delay on a crash, and it stops a second write while an earlier holder's write may still be in flight.
- **Known limits, recorded and not fixed in step 5.** The ledger table shares the task role's general table grant, which includes delete and scan. The completion write is not ledgered (above). The limits on the tool policy and the audit rows are listed in the [security model](../security-model.md#ai-steps-cannot-write-step-5). They are taken up in step 16 (security and audit depth).
- The held-request limit is measured, not assumed (decision 30), and the raw-IP path is re-proved at every digest bump. Failure behavior is specified in the [failure-handling matrix](../features/paperclip/minimum-sellable-product.md#j-minimum-testing-gate).

- **Reversibility:** two-way before the first live pack run; one-way after, because the effect-ledger key is a persisted schema that customer data depends on.
- **Revisit trigger:** the per-digest-bump hold test (a 45 s and a 250 s held response through the real hop to a raw private IP) fails at a digest that must be taken. Spike (a) failed as written on 2026-09-30, for a hostname; decision 30 is the rework.

## Alternatives considered

- **NATIVE_ASYNC_MONITOR** (Jev's first choice, 1.0). Revised away when the owner made true run states a blocker.
- **Forging 202 or 503 replies to pause work.** Rejected: they forge outcomes. Pause by disabling routines and agents.
- **AI steps that write.** Rejected: writes only in deterministic steps (Jev 0.99), so a retry cannot double-write.
- **Blind retry of an unknown-outcome write.** Rejected: `blocked: verify`.
- **A hostname for the dispatch address.** Rejected by decision 30: the new pin cuts a hostname dispatch at 30 s.
- **A patch that lifts the http adapter's timeout.** Not taken; held in reserve as the named fallback (ADR 0019 last resort, with an upstream issue).
