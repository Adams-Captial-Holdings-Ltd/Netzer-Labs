# ADR 0016 — Human decisions are recorded in Paperclip through shadow users; high-impact classes are human by default

**Status:** Accepted (owner-approved plan, 2026-09-26; recorded 2026-09-29; touched by decisions 18 and 31). Built in step 6 on the branch `feature/wp-step6-shadow-approvals`; not merged or deployed. Plan number 0015; repo number 0016 — [why](../features/paperclip/decision-log.md#adr-numbers).

## Context

Approvals are Paperclip's record of who allowed what, but Paperclip approvals are board-only. If Netzer approved on a person's behalf under a shared or operator account, the record would misidentify the approver, and a person could approve one action while another executes ([minimum sellable product](../features/paperclip/minimum-sellable-product.md), B5).

VERIFIED at plan time: board API keys are bound to a user (`board_api_keys.user_id`).

## Decision

1. **Each approver gets a headless Paperclip shadow user** with its own board key. The Netzer BFF writes to Paperclip as that shadow user: `approvals/:id/approve|reject`, or the pipeline `review` with `approve|reject|request_changes`. Netzer stays the identity authority ([ADR 0017](0017-netzer-identity-and-work-ui.md)). Step-2 spike (b) (2026-09-30) found that while sign-up is closed no user can be created, so approver accounts come from a **pool** (decision 31): one private sign-up window at setup, before any agent is live, creates the instance admin and a pool of inert approver accounts (about 25 proposed; the plan says at most 10 approvers at Customer #1), then sign-up is closed for good (`PAPERCLIP_AUTH_DISABLE_SIGN_UP=true`). A new approver takes one unused slot: rename it, mint a board key, never reuse a slot. The slot's password cannot be rotated: no password-change route is proven at the pinned Paperclip, so it stays in the secret (see "As built", A149). Overflow is a drained maintenance restart with a new window. A closed-sign-up probe runs after every deploy (an existing-email sign-up answers 422 when open and 400 when closed). The pool is built in step 6. Keys live in Secrets Manager. Rotation and RBAC sync are a staff runbook for ten or fewer approvers. In a customer's AWS account, what staff may do is set by decision 18 ([ADR 0017](0017-netzer-identity-and-work-ui.md)). There is no delegation engine in v1.
2. **Every decision carries** the approver (a real person via the shadow user), a timestamp, a comment (required for Reject and Request Changes, optional for Approve; owner, 2026-10-04, closes A74), the case and stage, and a Netzer audit row with the Netzer user ID, shadow ID, decision class and correlation IDs ([ADR 0020](0020-worm-audit-and-ledger-cost-authority.md)). The decisions are Approve, Reject and Request Changes. Paperclip enforces no comment rule, so Netzer enforces it.
3. **Frozen payload.** AI output is persisted once per `(case, stage, round)` and is never regenerated after approval is requested.
4. **Hash-bound approval.** The approval carries the sha256 of the exact L1 payload. The executor checks that hash and that `decidedByUserId` is a shadow user entitled to the decision class. Operator accounts never count.
5. **High-impact decision classes are human by default.** They need human sign-off unless the customer approved an automated-decision policy for that class (owner rule). Classes are declared as `decisionClasses` in `pack.json`; high-impact classes default to `human_required`. A customer exception is a recorded sign-off plus a config flag set by staff.
6. **Drift.** A reconcile job compares shadow users with Netzer identity and fails closed on mismatch. For the first customer (at most ten approvers) the reconcile job is the operator `check` command, run by staff before onboarding and after any rotation or role change; it exits non-zero on any mismatch between assigned slots and Netzer identity, and the executor's execution-time decider check and per-decision status check keep the approval path fail-closed in between; a scheduled in-service reconcile is deferred until approver count or change frequency justifies it.

**Decided by.** Approver identity: Jev split 0.57 to 0.43, so the owner decided: shadow users. Decision 31 (owner, 2026-09-30, after Jev was unsure at 0.28; council P3 first): the pool. Human gates: Jev 0.74, then the owner said YES with the rule in item 5. The blindspot review added the hash binding. Verified: `board_api_keys.user_id`. Step 6 (2026-10-04): the approval record was frozen by the owner ("Yes, freeze it"); the secret layout was frozen by the owner too ("One new secret" in the morning, then "Yes, split them" after the security review); the comment rule and "no network block of sign-up in this step" are the owner's; the other forks are in the [decision log](../features/paperclip/decision-log.md) (decisions 39 to 51).

### As built (step 6, 2026-10-04)

The code is a library plus an operator command line. Nothing here runs against a real Paperclip yet; the live proofs are PENDING (S6-L1 to S6-L5, listed under Consequences). Four decisions were taken on 2026-10-04 after the code review, when the code was at `79b06d0`. Where the code at `79b06d0` still differs, the text says "decided 2026-10-04; the code change is the review fix round that follows `79b06d0`" (the "review fix round" below).

- **The record (ONE-WAY, owner "Yes, freeze it", 2026-10-04).** An approval is a Paperclip classic approval of `type: 'request_board_approval'`. Its payload is exactly `{ netzerApproval: 1, payloadSha256, caseKey, stage, step, stageEntryNo, decisionClass }` and nothing else: never the payload itself, never text. `payloadSha256` is the sha256 of the L1 payload with sorted keys (the same hash the effect ledger uses, [ADR 0013](0013-sync-attach-execution-contract.md)). A record with another type, an extra or missing field, `netzerApproval` other than 1, a hash that is not 64 lower-case hex characters, or a key that fails the effect-key rules is not a Netzer approval (`not_a_netzer_approval`). The code is `src/lib/work/approvals.ts`.
- **Requesting.** `requestApproval({ key, payload, decisionClass })` validates the effect key and the class id (`^[a-z][a-z0-9_]*$`) before any call, creates the approval through the existing Paperclip client with the agent key, and writes the `approval_requested` audit row. It returns `{ approvalId, payloadSha256 }`.
- **Deciding.** Decisions are sent with Paperclip's `approve`, `reject` or `request-revision` route (Request Changes is `request-revision`), with the body `{ decisionNote }` and the approver's own board key as the bearer. An agent key never decides. `decide({ netzerUserId, approvalId, decision, comment })` runs these checks in this order, each before any Paperclip write, and each refusal throws `ApprovalRefusedError` with a code and writes a best-effort `approval_refused` audit row:
  1. The comment is trimmed. It must be non-empty for `reject` and `request_changes` (`comment_required`) and at most 4 000 characters (`comment_too_long`). It is optional for `approve`.
  2. The caller has an active shadow user (`not_an_approver`).
  3. The approval exists (`not_found`), is a Netzer approval (`not_a_netzer_approval`) and is `pending` (`not_pending`).
  4. The shadow user's `decisionClasses` list holds the approval's class (`class_not_entitled`).

  Then the slot's board key is read and the decision is sent. The record Paperclip returns must name the shadow user as `decidedByUserId`, or the call throws `ApprovalAttributionError` (at `79b06d0` without an audit row; the review fix round audits it). Last, the `approval_decided` audit row is written. If that write fails, the call fails, but the Paperclip decision stands and a repeat Approve is idempotent upstream. A key that cannot be read throws `ShadowKeyUnavailableError` (at `79b06d0`; the review fix round makes `decide` refuse with `paperclip_unavailable` or `key_unavailable` before any write).
- **The executor-side check.** `verifyApproval({ approvalId, key, payload, decisionClass })` reads the record live from Paperclip on every call (no cache) and throws `ApprovalInvalidError` with one of these codes: `paperclip_unavailable` (the read threw), `not_found`, `not_a_netzer_approval`, `not_approved` (any status but `approved`), `hash_mismatch` (the payload no longer matches the stored hash), `key_mismatch` (another case, stage, step or round), `class_mismatch`, `not_a_shadow_user` (no decider, or a decider with no shadow row: an operator, the instance admin, the lock auditor or an unassigned pool slot), `approver_retired` (decided after the shadow user's `retiredAt`, or the decision time is unreadable while the shadow user is retired) and `class_not_entitled`. `runApprovedEffect(executor, { approvalId, decisionClass, ...request })` runs `verifyApproval` first and `executor.runEffect` only after it passes, so no approval means no write. The executor is a library in step 6: it is not on the dispatch path (A140).
- **The secrets (ONE-WAY, owner "Yes, split them", 2026-10-04; supersedes the morning's one-secret layout; decided 2026-10-04; the code change is the review fix round that follows `79b06d0`).** The security review found that the running service could read every approver password, which it never needs. So there are two secrets, both outside `/<app>/paperclip*` (the deploy role's `PaperclipSecretPopulate` grant covers that prefix and must not reach approver credentials):
  - `/<app>/shadow-approvers` holds only the board keys: `{"v":1,"slots":{"<slot>":{"boardKey":string|null}}}`. It is the only one the orchestrator's task role may read: `secretsmanager:GetSecretValue` on this one secret ARN (statement `ShadowApproversRead`), no write action. The task learns the secret's id from the env value `SHADOW_APPROVERS_SECRET_ID` (the name, never the value). The secrets stack creates it with `{"v":1,"slots":{}}`.
  - `/<app>/shadow-approvers-setup` holds the slot logins: `{"v":1,"slots":{"<slot>":{"email":string,"password":string}}}`. It is read and written only with the operator's own credentials. No task-role grant and no CI or deploy-role grant reaches it.

  At `79b06d0` the code still has the morning's layout: one secret, `/<app>/shadow-approvers`, whose slot entries hold `email`, `password` and `boardKey`, so the task role can read the passwords. The split is the review fix round. In both layouts the reader (`createShadowKeyStore`) caches the map for 60 s and refetches once when a slot is missing from a cached map. It throws `ShadowKeyUnavailableError`, with the slot and nothing else in the message, when the secret cannot be read, is not JSON, is not `v: 1`, lacks the slot, or the key is null, empty or `REPLACE_ME`. A key or password never appears in an error message or a log line. The code is `src/lib/paperclip/shadow-keys.ts`, which validates the shape by hand because a source guard forbids `zod` under `src/lib/paperclip` (A151).
- **The registry rows** are in the existing users table (`TABLE_USERS`), not a new table (`src/lib/paperclip/shadow-rows-dynamo.ts`, types in `shadow-users.ts`):

  | Key | Holds |
  |---|---|
  | `PK = SHADOWSLOT#<slot>`, `SK = SLOT` | the slot, its Paperclip user id and its state: `free`, `assigned` or `retired` |
  | `PK = USER#<netzerUserId>`, `SK = SHADOW` | the shadow user for a Netzer user (forward lookup) |
  | `PK = PCUSER#<paperclipUserId>`, `SK = SHADOW` | the same shadow user for a Paperclip user (reverse lookup, used by `verifyApproval`) |

  A slot id is two digits, `01` to `99`. `00` is refused; it is kept for the lock auditor. Assign writes the slot row, the forward row and the reverse row in one transaction, conditional on the slot being `free`, on the Netzer user having no active shadow and on the reverse row being absent. Retire is one transaction that marks the slot and both rows `retired` with `retiredAt`; the reverse row stays, so an old decision still maps to its approver. No code path sets a slot back to `free`.
- **Entitlement** is a list of decision-class ids on the shadow row, set at assign time. `decide` and `verifyApproval` both check it. `requiresHumanApproval(decisionClasses, classId, automatedClasses)` is true unless the class is declared and either its `default` is `automated_allowed` or the customer's `automatedClasses` list names it; an unknown class id is true. `gateFor(policies, pipeline, stage)` returns the `decisionClass` of the pack's `approvalGates` entry, or nothing.
- **Audit.** `approval_requested`, `approval_decided`, `approval_refused`, `shadow_assigned`, `shadow_rotated` and `shadow_retired` are always-audited actions. Their details hold IDs and hashes only (a comment appears only as `commentSha256`; decided 2026-10-04, the hash is the sha256 of `<approvalId>` and a newline and the trimmed comment, and the code change is the review fix round that follows `79b06d0`, where it is the sha256 of the trimmed comment alone), never the comment, the payload, a key or an email.
- **The operator command line** is `npm run paperclip:shadow -- [--env=<name>] <command>` (`scripts/paperclip-shadow.ts`, logic in `scripts/lib/paperclip/shadow-core.ts`). It writes both secrets with the operator's own credentials. It signs in as the instance admin with `CCE_PAPERCLIP_ADMIN_EMAIL` and `PAPERCLIP_ADMIN_PASSWORD`; that session stays with the operator and never reaches the orchestrator (decision 32). In a customer's account, decision 18 says who runs it.
  - `pool [--size <n>]` (default 25, at most 99): inside the sign-up window, creates each missing slot (a sign-up for `shadow-<slot>-<hex>@netzer.invalid` with a random password), then writes the slot row and the secret entry with `boardKey: null` (at `79b06d0`, one entry holding the email, the password and `boardKey: null`; after the split, the login goes to the setup secret and the key entry to `/<app>/shadow-approvers`). A slot that already exists is left alone. It refuses with a plain message when sign-up is closed.
  - `assign --user <netzerUserId> --name <display name> --classes <a,b>`: the Netzer user must be active and have no active shadow. It takes the lowest free slot, signs in as the slot, renames it, mints a board key with no expiry, and the admin grants the company membership with the `operator` role (the lowest role that can decide; a `viewer` is read-only upstream). It checks the key's identity and the role, stores the key, writes the three rows in one transaction and audits `shadow_assigned`.
  - `rotate --user <netzerUserId>`: mints a second key with the first, stores the new one, deletes the old one, checks that the old one now answers 401 and audits `shadow_rotated`. It finds the current key by listing `GET /api/board-api-keys` and matching its name prefix; that list route was not exercised before and is unproven (A152).
  - `retire --user <netzerUserId>`: the admin removes the slot user's company access, the key entry is set to null, the rows go `retired` with `retiredAt`, and `shadow_retired` is audited. The slot is never reused.
  - `check`: for every assigned slot, the key must identify the recorded Paperclip user in the company and the Netzer user must be active. It prints the slot and a reason for each mismatch and exits non-zero.
  - `probe`: runs the closed-sign-up probe below; exit 0 only when sign-up is closed.
  - `list`: slot, state, Netzer user id and classes. No command prints a key, a password or an email.
- **Sign-up is closed by default.** The Paperclip task gets `PAPERCLIP_AUTH_DISABLE_SIGN_UP=true`. One switch opens a window for a deploy: `CCE_PAPERCLIP_SIGNUP_WINDOW=open`. With it set, the Paperclip task omits the flag and the orchestrator task gets `PAPERCLIP_SIGNUP_WINDOW=open`. The probe (`src/lib/paperclip/sign-up-probe.ts`) posts a sign-up for an address that already exists (the lock auditor's, from the `signup_probe_email` field the bootstrap writes to the Paperclip secret, injected as `PAPERCLIP_SIGNUP_PROBE_EMAIL`). A 400 with `EMAIL_PASSWORD_SIGN_UP_DISABLED` is clean. A 422 with `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`, or any 2xx, means sign-up is open: the verdict is `violated` with the code `sign_up_open`, or `unknown` with `sign_up_window_open` when the window is open. With no probe address the verdict is `unknown` (`sign_up_probe_email_missing`) and no request is sent. A 408, 429, 5xx, a network error or any other answer is `unknown` (`sign_up_probe_unprovable`); the probe never answers clean by default. It runs in the runtime lock at start and every 60 s ([ADR 0014](0014-netzer-only-ai-runtime.md)), and on demand with `probe`. **After a deploy, the check is the orchestrator's own start-time lock** (decided 2026-10-04, Jev 0.92; the code change is the review fix round that follows `79b06d0`): with sign-up open and no window, the new task refuses to start and the ECS circuit breaker fails the deploy. The deploy host cannot reach Paperclip's private address, so `scripts/deploy.ts` probes only when `PAPERCLIP_BASE_URL` (the tunnel) is set, and otherwise reports that it could not look. The deploy script itself is not what fails the deploy on open sign-up. At `79b06d0` the script still probes the private address after the service is stable, aborts on `sign_up_open` and only warns on an inconclusive result.
- **Password rotation (A149).** No password-change route is proven at the pinned Paperclip (there is none in `server/src`), so item 1's "rotate its password" is corrected: the slot password stays in the secret and the board key is what rotates. Proving or ruling out a route is the live proof S6-L4.
- **No network block of sign-up in this step** (owner, 2026-10-04). The flag and the probe are the controls.
- **The review fix round (decided 2026-10-04; the code change follows `79b06d0`).** Besides the secret split and the post-deploy check above: registry rows that do not validate are treated as absent, so verification fails closed; an attribution mismatch is audited (`approval_decided`, result `error`, code `attribution_mismatch`); `decide` refuses with `paperclip_unavailable` or `key_unavailable` before any write; the operator commands become resumable after a crash (`pool` writes the setup secret before the sign-up, `assign` and `rotate` recover a half-done run, `retire` can be re-run); and the command line resolves the users and audit table names from the environment suffix. At `79b06d0` none of these is in the code.
- **Known limit carried to step 7 (A153).** `decide()` trusts the `netzerUserId` its caller passes, and the task role can write the users table that holds the registry rows. Step 7's HTTP route must bind `netzerUserId` to the authenticated session and never take it from the request body. Registry-row write access is taken up in step 16.
- **Not built here:** the dashboard HTTP route that calls `decide` (step 7); the pipeline case review, so the `review` route in item 1 is not used (step 8 or later); the executor on the dispatch path (A140); a scheduled reconcile (item 6).

## Consequences

Good: the Paperclip record names the real person, and changing the payload after approval invalidates the approval.

Bad:

- Shadow-user sync can drift (Med). The reconcile job fails closed. At Customer #1 it is the manual `check` command plus the execution-time decider check and the per-decision status check (item 6).
- The shadow-user lifecycle is proven end to end with sign-up closed (spike (b) and decision 31), but the pool is a fixed size: overflow costs a drained maintenance restart.
- Paperclip enforces neither the hash nor the comment rule. Netzer enforces both, in `decide` and `verifyApproval`.
- A slot password cannot be rotated at the pinned Paperclip (A149). Until the secret split is built, the running service can read every slot password (the review finding behind the split).
- `decide()` trusts the `netzerUserId` its caller passes (A153, above).
- On a deployment whose Paperclip secret has no `signup_probe_email`, the bootstrap creates a new lock auditor, which needs sign-up open, so it must run inside the window; until the field exists the lock reads `unknown` and the Paperclip surface stays closed. The automatic staging deploy workflow has no window input (A150).
- **PENDING, not proved:** S6-L1 a real sign-up window (pool created, sign-up closed, the probe answers 400); S6-L2 assign a slot and approve with its key against a real Paperclip (`decidedByUserId` is the slot's user, `verifyApproval` passes, the operator's own approval is refused, and `rotate`'s key list works); S6-L3 the task role reads the board-key secret after a deploy and neither the task role nor the deploy role can read the setup secret; S6-L4 a password-rotation route; S6-L5 an ECS rollback to a revision with sign-up open closes the latch within one recheck. These run at the staging trip, never in this repository's tests.

- **Reversibility:** the approval record's shape and the two secret names and shapes are one-way since 2026-10-04 (owner), because customer approvals will live in Paperclip under that shape. The rest (the registry rows, the command line, the entitlement list, the probe) is two-way before approvals are recorded for a customer; one-way after, because approval records and attribution then live in Paperclip.
- **Revisit trigger:** approver churn makes pool overflow frequent (then a network-blocked open sign-up, or an upstream create-user route), or a rogue account is ever seen; step 8 installs pipelines (then the case review and the `review` route); Paperclip changes the approval payload contract at a digest that must be taken; per-slot isolation is required (then one secret per slot); approver count or change frequency grows (then a scheduled reconcile); step 11 maps SSO roles (then entitlement). Spike (b) failed as written on 2026-09-30; decision 31 is the rework.

## Alternatives considered

- **Approvals recorded under an operator or board account.** Rejected: it misidentifies the approver, and operator accounts never count.
- **Automated approval of high-impact decisions by default.** Rejected: human sign-off unless the customer's policy says otherwise.
- **A Netzer delegation engine.** Not built in v1.
- The plan records Jev's 0.57 to 0.43 split and the owner's choice of shadow users; it does not name the losing option.
- Step 6 forks (decisions 39 to 51), not taken: keys and passwords in one secret (decision 43 split them), keys inside the Paperclip secret (the deploy role's grant on `/<app>/paperclip*` would reach them), one secret per slot (kept as the revisit trigger), a probe that runs only after deploys (a circuit-breaker rollback is not a deploy), a deploy-script probe as the post-deploy check (the deploy host cannot reach Paperclip), and a network block of sign-up (the owner said not now). The other forks and the reasons are in the [decision log](../features/paperclip/decision-log.md).
