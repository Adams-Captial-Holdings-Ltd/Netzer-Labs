# ADR 0016 — Human decisions are recorded in Paperclip through shadow users; high-impact classes are human by default

**Status:** Accepted (owner-approved plan, 2026-09-26; recorded 2026-09-29; touched by decisions 18 and 31). Built in step 6 on the branch `feature/wp-step6-shadow-approvals`; not merged or deployed. Plan number 0015; repo number 0016 — [why](../features/paperclip/decision-log.md#adr-numbers).

## Context

Approvals are Paperclip's record of who allowed what, but Paperclip approvals are board-only. If Netzer approved on a person's behalf under a shared or operator account, the record would misidentify the approver, and a person could approve one action while another executes ([minimum sellable product](../features/paperclip/minimum-sellable-product.md), B5).

VERIFIED at plan time: board API keys are bound to a user (`board_api_keys.user_id`).

## Decision

1. **Each approver gets a headless Paperclip shadow user** with its own board key. The Netzer BFF writes to Paperclip as that shadow user: `approvals/:id/approve|reject`, or the pipeline `review` with `approve|reject|request_changes`. Netzer stays the identity authority ([ADR 0017](0017-netzer-identity-and-work-ui.md)). Step-2 spike (b) (2026-09-30) found that while sign-up is closed no user can be created, so approver accounts come from a **pool** (decision 31): one private sign-up window at setup, before any agent is live, creates the instance admin and a pool of inert approver accounts (about 25 proposed; the plan says at most 10 approvers at Customer #1), then sign-up is closed for good (`PAPERCLIP_AUTH_DISABLE_SIGN_UP=true`). A new approver takes one unused slot: rename it, mint a board key, never reuse a slot. The slot's password cannot be rotated: no password-change route is proven at the pinned Paperclip, so it stays in the secret (see "As built", A149). Overflow is a drained maintenance restart with a new window. A closed-sign-up probe runs in the orchestrator's runtime lock at start and every 60 s (an existing-email sign-up answers 422 when open and 400 when closed); the deploy script adds its own probe only when it can reach Paperclip. The pool is built in step 6. Keys live in Secrets Manager. Rotation and RBAC sync are a staff runbook for ten or fewer approvers. In a customer's AWS account, what staff may do is set by decision 18 ([ADR 0017](0017-netzer-identity-and-work-ui.md)). There is no delegation engine in v1.
2. **Every decision carries** the approver (a real person via the shadow user), a timestamp, a comment (required for Reject and Request Changes, optional for Approve; owner, 2026-10-04, closes A74), the case and stage, and a Netzer audit row with the Netzer user ID, shadow ID, decision class and correlation IDs ([ADR 0020](0020-worm-audit-and-ledger-cost-authority.md)). The decisions are Approve, Reject and Request Changes. Paperclip enforces no comment rule, so Netzer enforces it.
3. **Frozen payload.** AI output is persisted once per `(case, stage, round)` and is never regenerated after approval is requested.
4. **Hash-bound approval.** The approval carries the sha256 of the exact L1 payload. The executor checks that hash and that `decidedByUserId` is a shadow user entitled to the decision class. Operator accounts never count.
5. **High-impact decision classes are human by default.** They need human sign-off unless the customer approved an automated-decision policy for that class (owner rule). Classes are declared as `decisionClasses` in `pack.json`; high-impact classes default to `human_required`. A customer exception is a recorded sign-off plus a config flag set by staff.
6. **Drift.** A reconcile job compares shadow users with Netzer identity and fails closed on mismatch. For the first customer (at most ten approvers) the reconcile job is the operator `check` command, run by staff before onboarding and after any rotation or role change; it exits non-zero on any mismatch between assigned slots and Netzer identity, and the executor's execution-time decider check and per-decision status check keep the approval path fail-closed in between; a scheduled in-service reconcile is deferred until approver count or change frequency justifies it.

**Decided by.** Approver identity: Jev split 0.57 to 0.43, so the owner decided: shadow users. Decision 31 (owner, 2026-09-30, after Jev was unsure at 0.28; council P3 first): the pool. Human gates: Jev 0.74, then the owner said YES with the rule in item 5. The blindspot review added the hash binding. Verified: `board_api_keys.user_id`. Step 6 (2026-10-04): the approval record was frozen by the owner ("Yes, freeze it"); the secret layout was frozen by the owner too ("One new secret" in the morning, then "Yes, split them" after the security review); the comment rule and "no network block of sign-up in this step" are the owner's; the other forks are in the [decision log](../features/paperclip/decision-log.md) (decisions 39 to 51).

### As built (step 6, 2026-10-04)

The code is a library plus an operator command line. Nothing here has run against a real Paperclip or a real AWS account; the live proofs are PENDING (S6-L1 to S6-L5, listed under Consequences). The first build was `79b06d0`. A five-reviewer code and security review of it changed four decisions on 2026-10-04, and a review fix round built them in two commits: `fe2e891` (source and infrastructure) and `d7c599f` (scripts). This section describes the code after those two commits.

- **The record (ONE-WAY, owner "Yes, freeze it", 2026-10-04).** An approval is a Paperclip classic approval of `type: 'request_board_approval'`. Its payload is exactly `{ netzerApproval: 1, payloadSha256, caseKey, stage, step, stageEntryNo, decisionClass }` and nothing else: never the payload itself, never text. `payloadSha256` is the sha256 of the L1 payload with sorted keys (the same hash the effect ledger uses, [ADR 0013](0013-sync-attach-execution-contract.md)). A record with another type, an extra or missing field, `netzerApproval` other than 1, a hash that is not 64 lower-case hex characters, or a key that fails the effect-key rules is not a Netzer approval (`not_a_netzer_approval`). The code is `src/lib/work/approvals.ts`.
- **Requesting.** `requestApproval({ key, payload, decisionClass })` validates the effect key and the class id (`^[a-z][a-z0-9_]*$`) before any call, creates the approval through the existing Paperclip client with the agent key, and writes the `approval_requested` audit row. It returns `{ approvalId, payloadSha256 }`.
- **Deciding.** Decisions are sent with Paperclip's `approve`, `reject` or `request-revision` route (Request Changes is `request-revision`), with the body `{ decisionNote }` and the approver's own board key as the bearer. An agent key never decides. `decide({ netzerUserId, approvalId, decision, comment })` runs these checks in this order, each before any Paperclip write, and each refusal throws `ApprovalRefusedError` with a code and writes a best-effort `approval_refused` audit row (result `blocked`; a refusal survives an audit outage):
  1. The comment is trimmed. It must be non-empty for `reject` and `request_changes` (`comment_required`) and at most 4 000 characters (`comment_too_long`). It is optional for `approve`.
  2. The caller has an active shadow user (`not_an_approver`). A registry row that does not validate counts as no row.
  3. The approval is read from Paperclip. A read that throws is `paperclip_unavailable`. The approval must exist (`not_found`), be a Netzer approval (`not_a_netzer_approval`) and be `pending` (`not_pending`).
  4. The shadow user's `decisionClasses` list holds the approval's class (`class_not_entitled`).
  5. The slot's board key is read. If it cannot be read the refusal is `key_unavailable`.

  Then the decision is sent. A board key that is empty or holds whitespace or a control character is refused as `key_unavailable` before anything is sent. If Paperclip answers the decision with an HTTP 4xx, the call audits `approval_refused` with the audit-only code `paperclip_rejected` (best effort, result `blocked`) and throws the original error. For any other failure (a timeout, a network error, a 5xx, a closed lock) the outcome is unknown, because Paperclip may have applied the decision: the call audits `approval_refused` with the audit-only code `decision_outcome_unknown` (best effort, result `error`) and throws the original error. `verifyApproval` reads Paperclip live, so the executor still sees the true state. The record Paperclip returns must name the shadow user as `decidedByUserId`. If it names anyone else, the call writes an `approval_refused` audit row with result `error` and code `attribution_mismatch`, then throws `ApprovalAttributionError`. That case is never audited as `approval_decided`, and the other user's id is never recorded. Last, the `approval_decided` audit row is written. If that write fails, the call fails, but the Paperclip decision stands and a repeat Approve is idempotent upstream. The Paperclip port (`src/lib/work/approvals-paperclip.ts`) shape-checks every record it gets back (a non-empty string `id`, a string `type` and a string `status`), refuses a board key that holds whitespace or control characters, and turns a network failure or an unreadable body into `PaperclipApprovalHttpError`.
- **The executor-side check.** `verifyApproval({ approvalId, key, payload, decisionClass })` reads the record live from Paperclip on every call (no cache) and throws `ApprovalInvalidError` with one of these codes: `paperclip_unavailable` (the read threw), `not_found`, `not_a_netzer_approval`, `not_approved` (any status but `approved`), `hash_mismatch` (the payload no longer matches the stored hash), `key_mismatch` (another case, stage, step or round), `class_mismatch`, `not_a_shadow_user` (no decider, or a decider with no shadow row: an operator, the instance admin, the lock auditor or an unassigned pool slot), `approver_retired` (decided after the shadow user's `retiredAt`, or the decision time is unreadable while the shadow user is retired) and `class_not_entitled`. A registry row that does not validate is treated as absent, so a malformed row gives `not_a_shadow_user` and verification fails closed. `runApprovedEffect(executor, { approvalId, decisionClass, ...request })` runs `verifyApproval` first and `executor.runEffect` only after it passes, so no approval means no write. The executor is a library in step 6: it is not on the dispatch path (A140).
- **The secrets (ONE-WAY, owner "Yes, split them", 2026-10-04; supersedes the morning's one-secret layout).** The security review found that the running service could read every approver password, which it never needs. So there are two secrets, both outside `/<app>/paperclip*` (the deploy role's `PaperclipSecretPopulate` grant covers that prefix and must not reach approver credentials). The secrets stack creates both with `{"v":1,"slots":{}}`:
  - `/<app>/shadow-approvers` holds only the board keys: `{"v":1,"slots":{"<slot>":{"boardKey":string|null}}}`. It is the only one the orchestrator's task role may read: `secretsmanager:GetSecretValue` on this one secret ARN (statement `ShadowApproversRead`, in its own policy `ShadowApproversReadPolicy` on the task role), no write action. The task learns the secret's id from the env value `SHADOW_APPROVERS_SECRET_ID` (the name, never the value).
  - `/<app>/shadow-approvers-setup` holds the slot logins: `{"v":1,"slots":{"<slot>":{"email":string,"password":string}}}`. No service has a grant on it: not the task role, not the deploy role. Only the operator's own credentials read and write it.

  The reader (`createShadowKeyStore`) caches the map for 60 s and refetches once when a slot is missing or null in a cached map. It throws `ShadowKeyUnavailableError`, with the slot and nothing else in the message, when the secret cannot be read, is not JSON, does not validate as `v: 1` with `boardKey` entries, lacks the slot, or the key is null, empty or `REPLACE_ME`. A key or password never appears in an error message or a log line. The code is `src/lib/paperclip/shadow-keys.ts`, which validates the shape by hand because a source guard forbids `zod` under `src/lib/paperclip` (A151).
- **The registry rows** are in the existing users table (`TABLE_USERS`), not a new table (`src/lib/paperclip/shadow-rows-dynamo.ts`, types in `shadow-users.ts`):

  | Key | Holds |
  |---|---|
  | `PK = SHADOWSLOT#<slot>`, `SK = SLOT` | the slot, its Paperclip user id and its state: `free`, `assigned` or `retired` |
  | `PK = USER#<netzerUserId>`, `SK = SHADOW` | the shadow user for a Netzer user (forward lookup) |
  | `PK = PCUSER#<paperclipUserId>`, `SK = SHADOW` | the same shadow user for a Paperclip user (reverse lookup, used by `verifyApproval`) |

  A slot id is two digits, `01` to `99`. `00` is refused; it is kept for the lock auditor. Assign writes the slot row, the forward row and the reverse row in one transaction, conditional on the slot being `free`, on the Netzer user having no active shadow and on the reverse row being absent. Retire is one transaction that marks the slot and both rows `retired` with `retiredAt`; the reverse row stays, so an old decision still maps to its approver. No code path sets a slot back to `free`.
- **Entitlement** is a list of decision-class ids on the shadow row, set at assign time. `decide` and `verifyApproval` both check it. `requiresHumanApproval(decisionClasses, classId, automatedClasses)` is true unless the class is declared and either its `default` is `automated_allowed` or the customer's `automatedClasses` list names it; an unknown class id is true. `gateFor(policies, pipeline, stage)` returns the `decisionClass` of the pack's `approvalGates` entry, or nothing.
- **Audit.** `approval_requested`, `approval_decided`, `approval_refused`, `shadow_assigned`, `shadow_rotated` and `shadow_retired` are always-audited actions. Their details hold IDs and hashes only (a comment appears only as `commentSha256`, the sha256 of `<approvalId>`, a newline and the trimmed comment), never the comment, the payload, a key or an email. `approval_refused` rows carry one of the refusal codes above, or one of three codes that exist only in the audit: `paperclip_rejected` (result `blocked`), `decision_outcome_unknown` (result `error`) and `attribution_mismatch` (result `error`).
- **The operator command line** is `npm run paperclip:shadow -- [--env=<name>] <command>` (`scripts/paperclip-shadow.ts`, logic in `scripts/lib/paperclip/shadow-core.ts`). It uses the per-environment resources: the name suffix (`CCE_NAME_SUFFIX`, from the env file or the environment) picks the users table, the audit table and the three secrets, and the first line it prints names them. It reads and writes both secrets with the operator's own AWS credentials. It signs in as the instance admin with `CCE_PAPERCLIP_ADMIN_EMAIL` and `PAPERCLIP_ADMIN_PASSWORD`, and it needs `PAPERCLIP_BASE_URL` (the tunnel); that session stays with the operator and never reaches the orchestrator (decision 32). In a customer's account, decision 18 says who runs it. It exits 0 on success, 1 on a failed command or a failed `check` or `probe`, and 2 on a usage error. An error names the failed command (`<command> <ErrorName>`, with the HTTP status when there is one). If the action finished but its audit write failed, the line says so: `<command> done; the audit row was NOT written`. `pool`, `assign`, `rotate` and `retire` are resumable: run the same command again after a crash and it continues from what is already done.
  - `pool [--size <n>]` (default 25, 1 to 99): creates each missing slot and leaves an existing slot alone. For a new slot it first writes a login (`shadow-<slot>-<hex>@netzer.invalid` and a random password) to the setup secret, then signs up (or signs in, if the login already exists), then writes the slot row and a `boardKey: null` entry to `/<app>/shadow-approvers`. A crash between those steps is repaired by running `pool` again. Creating a Paperclip user needs the sign-up window; with sign-up closed it stops with "Pool can only be made inside the sign-up window". It prints `pool created <n>`.
  - `assign --user <netzerUserId> --name <display name> --classes <a,b>`: the Netzer user must be active. If the user already has an active shadow, it sets the Paperclip display name again, audits and prints the slot; it fails and changes nothing when the requested classes differ from the stored ones (retire, then assign). Otherwise it takes the lowest free slot, uses the stored board key if that key is valid and the only live key of the slot, and otherwise signs in with the setup login, mints a key with no expiry and stores it. Every assign run sets the slot user's display name. The admin grants the company membership with the `operator` role (the lowest role that can decide; a `viewer` is read-only upstream). It checks the key's identity and the role, writes the three rows in one transaction and audits `shadow_assigned`. A crash before the transaction leaves the slot `free`, so the same command takes the same slot and reuses the stored key.
  - `rotate --user <netzerUserId>`: mints a second key with the current key (or with the setup login when the current key no longer works), stores the new one, deletes the older ones, checks that the old one now answers 401 or 403 and audits `shadow_rotated`. A repeat run rotates again. It finds the current keys by listing `GET /api/board-api-keys` and matching the name prefix `netzer-shadow-<slot>-`; that list route was not exercised before and is unproven (A152).
  - `retire --user <netzerUserId>`: the admin removes the slot user's company access, the command checks the stored key no longer reaches the company, the rows go `retired` with `retiredAt`, the command tries to revoke the slot's board key in Paperclip (best effort; it prints `<slot> key_revoke_failed` and goes on when it cannot), the key entry is set to null, and `shadow_retired` is audited. The slot is never reused. If the rows are already retired and the key entry is null, a repeat run only audits.
  - `check`: for every assigned slot, the key must identify the recorded Paperclip user in the company and the Netzer user must be active. It prints the slot and a reason for each mismatch (`key_missing`, `user_missing`, `user_inactive`, `key_invalid`, `identity_mismatch`, `paperclip_unreachable`) and exits 1. It prints `<slot> row_invalid` and exits 1 when a slot the secret knows has no valid slot row, or when an assigned slot's forward or reverse user row is absent or names another slot. It also exits 1 with `secret_unreadable` when the key secret cannot be read, with `secret_invalid` when it does not validate, and with `no slot rows found in table <name>` when the users table holds no slot rows, which usually means the wrong environment.
  - `probe`: reads `signup_probe_email` from the Paperclip secret and runs the closed-sign-up probe below. It prints `clean` or the reason code, and exits 0 only when sign-up is closed.
  - `list`: slot, state, Netzer user id and classes. A slot whose rows do not validate is printed as `invalid`. No command prints a key, a password or an email.
- **Sign-up is closed by default.** The Paperclip task gets `PAPERCLIP_AUTH_DISABLE_SIGN_UP=true`. One switch opens a window for a deploy: `CCE_PAPERCLIP_SIGNUP_WINDOW=open`. With it set, the Paperclip task omits the flag and the orchestrator task gets `PAPERCLIP_SIGNUP_WINDOW=open`. The probe (`src/lib/paperclip/sign-up-probe.ts`) posts a sign-up for an address that already exists (the lock auditor's, from the `signup_probe_email` field the bootstrap writes to the Paperclip secret, injected as `PAPERCLIP_SIGNUP_PROBE_EMAIL`). A 400 with `EMAIL_PASSWORD_SIGN_UP_DISABLED` is clean. A 422 with `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`, or any 2xx, means sign-up is open: the verdict is `violated` with the code `sign_up_open`, or `unknown` with `sign_up_window_open` when the window is open. With no probe address the verdict is `unknown` (`sign_up_probe_email_missing`) and no request is sent. A 408, 429, 5xx, a network error or any other answer is `unknown` (`sign_up_probe_unprovable`); the probe never answers clean by default. It runs in the runtime lock at start and every 60 s ([ADR 0014](0014-netzer-only-ai-runtime.md)), and on demand with `probe`. **After a deploy, the check is the orchestrator's own start-time lock** (decided 2026-10-04, Jev 0.92): with sign-up open and no window, the new task refuses to start and the ECS circuit breaker fails the deploy. The deploy host cannot reach Paperclip's private address, so `scripts/deploy.ts` probes only when `PAPERCLIP_BASE_URL` (the tunnel) is set (`runPostDeploySignUpProbe`, in `scripts/lib/lifecycle/sign-up-deploy-probe.ts`). With it set, an open sign-up aborts the deploy with `sign_up_open`, a closed one prints that sign-up is closed, and an inconclusive result prints a warning with its code. Without it, the script prints that the deploy host cannot reach Paperclip and that the orchestrator proves sign-up closed at start and refuses to start if it is open. In that case the orchestrator, not the deploy script, is what fails the deploy.
- **Password rotation (A149).** No password-change route is proven at the pinned Paperclip (there is none in `server/src`), so item 1's "rotate its password" is corrected: the slot password stays in the secret and the board key is what rotates. Proving or ruling out a route is the live proof S6-L4.
- **No network block of sign-up in this step** (owner, 2026-10-04). The flag and the probe are the controls.
- **The review fix round (decided 2026-10-04; built in `fe2e891` and `d7c599f`).** Besides the secret split and the post-deploy check above: registry rows that do not validate are treated as absent, so verification fails closed; every refusal and an attribution mismatch leave an audit row (`attribution_mismatch` is `approval_refused` with result `error`, never `approval_decided`); `decide` refuses with `paperclip_unavailable` or `key_unavailable` before any write; the Paperclip port shape-checks the records it gets back; the operator commands are resumable after a crash; the command line resolves the users and audit table names from the environment suffix and no longer runs when imported; and the bootstrap reuses a valid lock auditor key (`--new-auditor` forces a new one). Three environment variables are registered in `docs/deprecations.json`: `PAPERCLIP_SIGNUP_PROBE_EMAIL`, `PAPERCLIP_SIGNUP_WINDOW` and `SHADOW_APPROVERS_SECRET_ID`. None of it has run against a real Paperclip or a real AWS account.
- **Known limit carried to step 7 (A153).** `decide()` trusts the `netzerUserId` its caller passes, and the task role can write the users table that holds the registry rows. Step 7's HTTP route must bind `netzerUserId` to the authenticated session and never take it from the request body. Registry-row write access is taken up in step 16.
- **Not built here:** the dashboard HTTP route that calls `decide` (step 7); the pipeline case review, so the `review` route in item 1 is not used (step 8 or later); the executor on the dispatch path (A140); a scheduled reconcile (item 6).

## Consequences

Good: the Paperclip record names the real person, and changing the payload after approval invalidates the approval.

Bad:

- Shadow-user sync can drift (Med). The reconcile job fails closed. At Customer #1 it is the manual `check` command plus the execution-time decider check and the per-decision status check (item 6).
- The shadow-user lifecycle is proven end to end with sign-up closed (spike (b) and decision 31), but the pool is a fixed size: overflow costs a drained maintenance restart.
- Paperclip enforces neither the hash nor the comment rule. Netzer enforces both, in `decide` and `verifyApproval`.
- A slot password cannot be rotated at the pinned Paperclip (A149). The passwords sit in the setup secret, which no service can read.
- `decide()` trusts the `netzerUserId` its caller passes (A153, above).
- On a deployment whose Paperclip secret has no `signup_probe_email`, the lock reads `unknown` (`sign_up_probe_email_missing`) and the Paperclip surface stays closed. The bootstrap reuses a valid lock auditor key and prints that the probe address is unknown; `--new-auditor` makes it create a new auditor and write the address. A new auditor needs sign-up open, so that run must be inside the window. The automatic staging deploy workflow has no window input (A150).
- **PENDING, not proved:** S6-L1 a real sign-up window (pool created, sign-up closed, the probe answers 400); S6-L2 assign a slot and approve with its key against a real Paperclip (`decidedByUserId` is the slot's user, `verifyApproval` passes, the operator's own approval is refused, and `rotate`'s key list works); S6-L3 the task role reads the board-key secret after a deploy and neither the task role nor the deploy role can read the setup secret; S6-L4 a password-rotation route; S6-L5 an ECS rollback to a revision with sign-up open closes the latch within one recheck. These run at the staging trip, never in this repository's tests.

- **Reversibility:** the approval record's shape and the two secret names and shapes are one-way since 2026-10-04 (owner), because customer approvals will live in Paperclip under that shape. The rest (the registry rows, the command line, the entitlement list, the probe) is two-way before approvals are recorded for a customer; one-way after, because approval records and attribution then live in Paperclip.
- **Revisit trigger:** approver churn makes pool overflow frequent (then a network-blocked open sign-up, or an upstream create-user route), or a rogue account is ever seen; step 8 installs pipelines (then the case review and the `review` route); Paperclip changes the approval payload contract at a digest that must be taken; per-slot isolation is required (then one secret per slot); approver count or change frequency grows (then a scheduled reconcile); step 11 maps SSO roles (then entitlement). Spike (b) failed as written on 2026-09-30; decision 31 is the rework.

## Alternatives considered

- **Approvals recorded under an operator or board account.** Rejected: it misidentifies the approver, and operator accounts never count.
- **Automated approval of high-impact decisions by default.** Rejected: human sign-off unless the customer's policy says otherwise.
- **A Netzer delegation engine.** Not built in v1.
- The plan records Jev's 0.57 to 0.43 split and the owner's choice of shadow users; it does not name the losing option.
- Step 6 forks (decisions 39 to 51), not taken: keys and passwords in one secret (decision 43 split them), keys inside the Paperclip secret (the deploy role's grant on `/<app>/paperclip*` would reach them), one secret per slot (kept as the revisit trigger), a probe that runs only after deploys (a circuit-breaker rollback is not a deploy), a deploy-script probe as the post-deploy check (the deploy host cannot reach Paperclip), and a network block of sign-up (the owner said not now). The other forks and the reasons are in the [decision log](../features/paperclip/decision-log.md).
