## 3. Codebase understanding

### 3.1 Architecture notes discovered this session

Findings that carry an ID (A76-A82, M82) in section 5.28 were re-checked with `grep` or a command on 2026-09-30 at `c9897c5`. The rest comes from read-only explorer reports and needs a `grep -n` at your own commit before you cite a line (A73).

- **The Paperclip test lane is manual and thin.** `tests/contract/paperclip-routes.paperclip.integration.test.ts` (23 tests) and `src/lib/paperclip/client.paperclip.integration.test.ts` (2 tests) run only when `PAPERCLIP_TEST_AUTH_SECRET` is set, against `docker-compose.paperclip.yml`. `npm test` excludes `*.integration.test.ts`, no workflow supplies the variable, and no test drives the real `PaperclipClient` against a real server: every covered route is a raw `fetch` probe. `tests/contract/paperclip/` does not exist (A72 still holds).
- **Deleting the patch breaks no test.** No test asserts `updated-since.patch`, the `patch` install, the `tsc` re-emit or the UI symlink in `vendor/paperclip/Dockerfile`. It does break two docs gates (the front-matter link in `docs/features/paperclip/README.md` and three markdown links to the patch) and the `.gitattributes` rule. The danger is behavior: the reconciler's boot probe (`runBootProbe`) reads "an offset-less `updatedSince` returns 400" as proof that the patch is present. If the new digest accepts it natively, the probe latches `boot-probe-failed` and the reconciler never sweeps again. The reconciler's keyset paging was also reasoned against the patch's `>=` predicate. Both have to be re-derived from the contract suite before the bump.
- **The runtime lock is all new code.** ADR 0014 names five conditions (native runner off, no non-`http` adapter, no remote profiles, tool access off, timer heartbeats off on pack agents) plus telemetry off. None exists as code (A78). The instance-settings and scheduler routes are board-only, while the orchestrator holds only agent keys, so the spec must say which credential reads them or run the check inside the Paperclip task.
- **A startup gate would be the first async fail-closed gate in `main()`** (`src/index.ts`). Every async boot step today is fail-open, and `startPaperclipReconciler()` is the nearest precedent: a three-valued verdict that refuses only the sweep, never the process. Paperclip rolls at `minHealthyPercent: 0` and the orchestrator has `circuitBreaker: { rollback: true }`, so a hard "unknown means refuse" would crash-loop the orchestrator during any Paperclip roll. The verdict needs an explicit unknown case.
- **Dispatch has no private address, and the public route can only be denied in code** (A80).
- **The Paperclip client has no outbound allowlist** (A81).
- **Two deploy drivers exist:** `scripts/deploy.ts` (local) and `.github/workflows/deploy.yml` (CI). A deploy-time check needs both, plus a cross-driver text test like the ones in `scripts/lib/lifecycle/paperclip-image-pipeline.test.ts`. Preflight cannot host a fail-closed check because `--skip-preflight` bypasses it.
- **The image tag comes from the committed tree.** `contentImageTag` in `scripts/lib/lifecycle/cloud-build.ts` hashes only committed files under `vendor/paperclip/`, and the skip path refuses a dirty tree, so commit `vendor/paperclip` before any deploy.
- **Registry facts** (A77): the old tag is gone but its digest resolves; the new digest and both sizes are recorded there.

### 3.4 Spike results (measured 2026-09-30, sealed containers)

Both Paperclip images were pulled by digest (A77) and run with `--network none`, embedded Postgres and throwaway secrets, one hermetic container per run. The rig (a receiver that holds responses, two drivers and two shell scripts) is operator-local under `~/.claude/plans/netzer-work-platform/spikes/`; the raw logs are in `~/.claude/plans/netzer-work-platform-logs/` (`s2-spike-*`, summary in `s2-spike-results.md`). "Hung up after" is measured on the receiver's side.

**Spike (a), a dispatch held open for six minutes or more: FAIL at both pins (A83).**

| Pin | URL kind | Hold | Paperclip hung up after | Run result |
|---|---|---|---|---|
| v2026.916.1 (new) | hostname | 20 s | never (answered) | succeeded |
| v2026.916.1 | hostname | 45 s | 30.0 s | failed, "HTTP adapter endpoint did not respond in time" |
| v2026.916.1 | hostname | 380 s | 30.0 s | failed, same error |
| v2026.916.1 | raw IP | 45 s | never (answered) | succeeded |
| v2026.916.1 | raw IP | 380 s | 302.2 s | failed, "fetch failed" |
| v2026.722.0 (old) | hostname or raw IP | 20 s or 45 s | never | succeeded |
| v2026.722.0 | hostname | 380 s | 302.5 s | failed, "fetch failed" |
| v2026.722.0 | raw IP | 380 s | 302.5 s | failed, "fetch failed" |

A follow-up sealed run at the new pin (logs `s2-spike-a2-916-*`) held the response just under each ceiling. A raw-IP dispatch held 240 s and 280 s succeeded (the receiver answered at 240.0 s and 280.0 s), and a hostname dispatch held 25 s and 29 s succeeded. So ADR 0013's attempt cap of about 240 s does work over a raw IP at the new pin, with about 60 s to spare against the roughly 300 s ceiling.

The cause, read in source and confirmed by the runs: the new pin sends http-adapter calls through a guarded transport whose response-headers deadline is a hard 30 s (`DEFAULT_RESPONSE_TIMEOUT_MS = 30_000` in `server/src/services/remote-http-fetch.ts`), and `adapters/http/execute.ts` passes no override. A raw-IP URL skips that transport and gets the platform fetch default of about 300 s, which is also what every URL got at the old pin. The adapter counts the run as done when 2xx headers arrive and never reads the body. Its own `timeoutMs` only aborts earlier; it cannot lengthen the deadline. ADR 0013's planned attempt cap of about 240 s is therefore reachable only with a raw-IP dispatch URL (proven for 240 s and 280 s by the follow-up run above). The request body at the new pin also carries context keys the old pin did not send (`responsibleUserId`, `originIdentityContextId`, `executionIdentityRunId`, `executionContinuation`, `paperclipWake`, `githubAuthenticationMode`).

**Spike (b), the shadow-user lifecycle at the new pin: FAIL as written, "sign-up closed, create" (A84).**

- Sign-up closed from a fresh database: `POST /api/auth/sign-up/email` returns 400 `EMAIL_PASSWORD_SIGN_UP_DISABLED`, sign-in returns 401, and `/api/health` stays `bootstrap_pending`. No user can exist, so not even the first admin can be created. The flag is read only at boot.
- Sign-up open, the whole chain works: sign-up and sign-in; `POST /api/bootstrap/claim` makes the first user the instance admin; a company; a shadow user that mints its own board key (`pcp_board_...`, no expiry accepted); membership added by the instance admin with `PUT /api/admin/users/:id/company-access` (role `operator`); an approval whose payload carries a `payloadSha256` keeps the hash intact on read; approve with the shadow key records `decidedByUserId` as the shadow user; a repeat approve is 200 and idempotent; reject after approve is 422; key rotation (mint a second key with the first, the shadow deletes the old one, the old key gets 401 on the next call); a membership archive takes effect on the next request (`companyIds` empty, approve 404); re-adding restores the prior role.
- Paperclip has no admin route to create or delete a user (`DELETE /api/admin/users/:id` is 404) and none to list, mint or revoke another user's board key. An admin cannot delete a shadow user's key (404).
- A brand-new user has no company access until an instance admin adds it, so an open sign-up on a private instance creates inert rows.
- The same database restarted with sign-up closed: existing users sign in and their keys keep working and can approve; a new user still cannot be created.
- Rejecting without a comment returns 200, so the comment is not enforced on classic approvals (A86, bears on A74).

**Spike (b3), a dry run of the pool option for B5 (P3): it works end to end at the new pin (A91).** Sealed containers again (logs `s2-spike-b3-*`). With sign-up open, an admin was created and claimed, and three inert pool users were created. The same database was then restarted with sign-up closed: a pool user signed in, was renamed with `PATCH /api/auth/profile` (the name changed, the email stayed the placeholder), minted its own board key, was added to the company by the admin, and approved with that key (`decidedByUserId` is the pool user, and the company user directory shows the new name). An unassigned pool user can mint a key but sees no company (`companyIds` empty, approvals list 403). A side-effect-free way to check that sign-up is closed: post a sign-up for an email that already exists. It returns 422 `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` while sign-up is open (no user is created) and 400 `EMAIL_PASSWORD_SIGN_UP_DISABLED` once it is closed.

**Spike (c), importing an agent bundle into an existing company: it works, with one dangerous default (A92, A93).** Sealed container, logs `s2-spike-c.log` and `s2-spike-c2.log`. A bundle of `COMPANY.md` plus two `AGENTS.md` files, `existing_company` as the target, `include.company` false and `skip` as the collision strategy: the preview shows no errors and lists the agents' adapter as `process`, the import with an `adapterOverrides` entry per agent creates both agents as `http` with the given URL, heartbeats disabled and `maxConcurrentRuns` 20, and an identical second import skips both and changes nothing. A missing `COMPANY.md` returns 422, the `rename` strategy creates duplicates ("Research 2"), and `include.company` true renames the company to the bundle's name. The dangerous default: when one agent has no override, the import still succeeds and creates that agent as `process`. A second container with the adapter allowlist `PAPERCLIP_ADAPTERS='[{"adapterType":"http"}]'` gave the same result (creating a `process` agent directly is refused with 422, the import path is not), and a later import with both overrides then skipped both and left the `process` agent in place.

**Spike (d), concurrency and routine defaults: confirmed, with one failure mode (A94, A95).** Sealed containers, logs `s2-spike-d.log` and `s2-spike-d2.log`. The per-agent `maxConcurrentRuns` defaults to 20 and an explicit 1 is respected: three wakes on a cap-1 agent ran one at a time in `createdAt` order and all succeeded, and 24 wakes on a default agent gave 20 running and 4 queued. A routine defaults to `coalesce_if_active` and `skip_missed`. With the same revision and an identical payload while the first issue is live, `coalesce_if_active` returns `coalesced`, `skip_if_active` returns `skipped`, and `always_enqueue` returns a failed run with a raw database error; a different payload creates a new issue under all three. Changing the policy creates a new routine revision, so two runs on either side of a PATCH never collide.

**Runtime-lock levers verified at the new pin (A85).**

- A fresh instance has `enableNativeRunner` true. `PATCH /api/instance/settings/experimental {"enableNativeRunner":false}` returns 200 and persists. With `PAPERCLIP_HIDDEN_SETTINGS=instance.experimental.enableNativeRunner,instance.adapters,instance.plugins`, setting it back to true returns 403 `settings_operator_managed`, and the unauthenticated `GET /api/health` lists `hiddenSettings`.
- With `PAPERCLIP_ADAPTERS='[{"adapterType":"http"}]'` every other adapter type is unavailable: creating a `claude_local` or `process` agent returns 422, `paperclip_runner` returns 422, `http` returns 201.
- A fresh database has no built-in agents (`enableBuiltInAgents` is false and a new company's agent list is empty), so A79's two paused `claude_local` agents exist only on databases created at the old pin, such as the live instance. A fresh install does have one default "Local" environment (driver `local`, managed by Paperclip) that no lock condition mentions.
- Remote agent profiles, managed agent profiles, tool gateways, connections, applications, routines and scheduler heartbeats are all empty on a fresh instance.
- The private-target allowlist accepted `PAPERCLIP_HTTP_ADAPTER_PRIVATE_ENDPOINT_ALLOWLIST="http://localhost:9091,http://127.0.0.1:9091"`: bare origins with the port (A88).

**Read in source at the new pin, not run (A87, A88, A89).** The read-only explorers found these; take a `grep -n` at your own commit before citing a line (A73).

- Telemetry off is `PAPERCLIP_TELEMETRY_DISABLED=1`, `DO_NOT_TRACK=1` (the exact string `1`) and `PAPERCLIP_ANNOUNCEMENTS_ENABLED=false`, plus the feedback preference `not_allowed`.
- The guard's allowlist drops path entries and always denies link-local addresses.
- The new pin brings 96 migrations, some of them irreversible drops, and unattended boots need `PAPERCLIP_MIGRATION_PROMPT=never`, so the re-pin is one-way for the database and the rollback is a snapshot restore.
- Native `updatedSince` is a strict `>` and accepts an offset-less value as local time. The patch no longer applies at the new pin, and the reconciler's boot probe would misread the new behavior (section 3.1).

### 5.1 Process precautions

| # | Precaution | Why it exists |
|---|---|---|
| P1 | Record a baseline before changing anything. | Without it a pre-existing failure is indistinguishable from a regression you caused. |
| P2 | Never record a command as passing unless it actually ran. Say what you skipped and why. | See M5: a handoff once carried checks that no runtime could have executed. |

| P5 | When a document and the code disagree, **the code wins**. Fix the document. | The framework's stated tie-break. |
| P6 | Never force-add unrelated uncommitted work you find in the tree. Preserve it and hand it back to its owner. | Stray files found during cleanup are somebody's in-flight work, not yours to merge. |
