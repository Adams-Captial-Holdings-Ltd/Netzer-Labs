## 3. Codebase understanding

### 3.1 Architecture notes discovered this session

- **Paperclip's private-hostname guard is mounted in front of everything, `/api/health` included** (`server/src/app.ts` at `v2026.722.0`: `shouldEnablePrivateHostnameGuard` = exposure `private` and mode `local_trusted` or `authenticated`; `app.use(privateHostnameGuard(...))` before the health sub-route and the `/api` router). It compares `URL.hostname` (no port), reads `x-forwarded-host` before `Host` (so a forged forwarded header bypasses it; never use that as a workaround), and its allow list is `PAPERCLIP_ALLOWED_HOSTNAMES` (comma list, lowercased, **replaces** `config.json`'s list) plus the public-URL hostname.
- **Bind mode beats `HOST`.** `server/src/config.ts:181-191`: `bind = PAPERCLIP_BIND ?? fileConfig.server.bind ?? inferBindModeFromHost(HOST)`; `packages/shared/src/network-bind.ts` `resolveRuntimeBind`: `loopback` → `127.0.0.1`, `lan` → `0.0.0.0`; `validateConfiguredBindMode` allows `lan` for `authenticated`/`private`. The container health check hits `127.0.0.1` (`infra/lib/paperclip-stack.ts:497`), so a loopback-only listener is invisible to ECS, CloudFormation and the deploy.
- **Who wrote `server.bind: loopback` into the EFS `config.json` is not identified.** `auth bootstrap-ceo` only reads the file (`cli/src/commands/auth-bootstrap-ceo.ts`); quickstart onboarding would have written `lan` from `HOST=0.0.0.0` (`cli/src/commands/onboard.ts:163-171`); the server's runtime API does not write it. The durable answer is the same regardless: every knob the file can override is set on the task definition.
- **Cloud Map is the only route to Paperclip** (no target group; A record, 15 s TTL, task ENI IP, `paperclip-stack.ts:579-620`), so a loopback-only listener produces a connection failure, not an HTTP error — exactly the probe's `request-failed-before-response`.
- **ECS forgets stopped tasks after about an hour.** Find a probe task through CloudWatch instead: `describe-log-streams --order-by LastEventTime --descending` (the API refuses a prefix together with that ordering), then `filter-log-events` for `PAPERCLIP_PHASE_PROBE`. The probe task's stream holds only the probe lines.
- **The emulated arm64 image build sits on npm's socket-inactivity timeout.** The `[build]` stage (devDependencies, `aws-cdk-lib` included, under QEMU) took 259 s in the bar run and died at 266-274 s with `read ETIMEDOUT` in two consecutive attempts, after an 83-minute stall in a third; `deps` and `web` stage timings matched the bar to the second. Lockfiles and Dockerfile unchanged since `ac70509`. Re-running was the remedy; the fix is one `npm_config_fetch_timeout` line or not installing `aws-cdk-lib` in the image build.
- **A staging round trip is about an hour** (9 min image build, 2 min migrate, 1.5-11 min CDK deploy depending on whether the Paperclip task is replaced, 2.5 min rollout, 1 min probe) and the ladder (three PRs, three check rounds) about 15 min. `aws login` sessions expire in roughly two hours, which is less than one finding-fix-redeploy cycle.

### 3.3 Patterns and conventions to follow

- When a private service is reached through a tunnel, force the real Host header at least once (`curl -H "Host: paperclip.claudeclaw-staging.internal:3100" http://127.0.0.1:3100/...`); the tunnel's loopback Host hides hostname- and origin-based guards.
- Read a probe failure code literally: `request-rejected (HTTP n)` means Paperclip answered; `request-failed-before-response` means no TCP/HTTP answer at all.
- Test-first for infrastructure too: write the literal assertion on the synthesized template, watch it fail on `undefined`, add the one line, watch it pass.
- Promotion ladders as a gated script (`wait_checks` per rung, merge only on all-pass, poll the Deploy run): three merges and a 30-minute deploy without a human in the loop, and an `ABORT` line if any rung is not green.
- Re-run a documented flaky test in isolation before calling it a regression (`src/adapters/dashboard/jarvis.flow.test.ts`, 18/18 alone after failing under concurrent load).
