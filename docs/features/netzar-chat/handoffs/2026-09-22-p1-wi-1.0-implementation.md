## 3. What was built

`isConversationRow` in [`handler.ts`](../../../../src/adapters/dashboard/handler.ts), applied at all
four readers of the shared `claudeclaw-sessions` table. Three lines of predicate, three `.filter(…)`

### 3.1 The four readers, re-derived at their lines

| Reader | Read | Mapping | Now |
|---|---|---|---|
| `GET /sessions`, per-agent | `Query`, `KeyConditionExpression: 'PK = :pk'` (`handler.ts:2074-2081`) | `:2099` | filtered |
| `GET /sessions`, cross-agent | `Scan`, `Limit: 100` (`:2089-2095`) | same `:2099` | filtered |
| `GET /sessions/export` | paged `Scan` to 10,000 (`:3669-3678`) | `:3682` | filtered |

The first two share one `.map()`, so three call sites cover four readers.

### 3.2 The inference became a measurement

The SPECIFICATION could only **infer** (A130) that a Jarvis memory row renders as a conversation.
It is now **Observed**: with the table holding one conversation row, one `CHAT#…#MSG#…` row and one
`PK=JARVIS#…`, `SK=TURN#…` row, the cross-agent `GET /sessions` returned **3** sessions before the
fix and **1** after. The export returned 4 CSV lines and now returns 2. The jarvis action returned
3 and now returns 1.

That also names the disclosure this closes, which nobody had stated before: the Jarvis row rendered
with `agentId: JARVIS#<hashPrefix16>` — the principal's own id — to any holder of `sessions:read`,
the lowest tier that can call the route. The independent security review re-derived `hashPrefix16`
as the first 16 hex characters of `sha256(bearerToken)` (`dashboard-auth.ts:123,145`) and confirmed
the `ProjectionExpression` never requested the Jarvis row's `text`, so no memory **content** was
reachable — only the id and the turn's timestamp and uuid.

### 3.3 Why an allowlist, and what it rests on

The rule is the conversation key shape — `PK=AGENT#…`, `SK=CHAT#<chatId>` with no further `#`
segment — not a blocklist of the foreign types that exist today. A blocklist has to be extended for
every future item type, and the one that gets forgotten is the failure this gate exists to prevent.
P3 adds attachments, so "one more item type" is not hypothetical.

**It rests on chatIds carrying no `#`, and section 6.2 is where that assumption breaks.**

### 5.1 Process precautions

| # | Precaution | Why it exists |
|---|---|---|
| P1 | Record a baseline before changing anything. | Without it a pre-existing failure is indistinguishable from a regression you caused. |
| P2 | Never record a command as passing unless it actually ran. Say what you skipped and why. | See M5: a handoff once carried checks that no runtime could have executed. |
| P3 | Name the branch. Never write "ready for production". | Four long-lived branches exist and only two reach an AWS environment. |
| P4 | Run the FULL `npm test` before pushing, never a scoped run. | Required by [`CLAUDE.md`](../../../../CLAUDE.md). Scoped runs have hidden cross-module regressions here. |
| P5 | When a document and the code disagree, **the code wins**. Fix the document. | The framework's stated tie-break. |
| P6 | Never force-add unrelated uncommitted work you find in the tree. Preserve it and hand it back to its owner. | Stray files found during cleanup are somebody's in-flight work, not yours to merge. |
| P7 | Delete a transient branch once it merges. | Only `development`, `qa`, `staging`, `production` survive, so a handoff that names a branch names something that still exists. |
| P8 | Docs changes must pass `node scripts/ci/feature-knowledge.mjs` and `node scripts/ci/docs-links.mjs` before pushing. | Docs CI runs them anyway; failing there costs a round trip. |
| P9 | Never restate feature-documentation rules outside [the framework](../../README.md). | A second copy is exactly how these conventions drifted before — see M1. |

**Built WI-1.0 and nothing else.** No storage change, no ownership change, no new item type —
owner decision 11 gates all three behind this work item.

### 6.1 The shape of the change

Two production files. `handler.ts` gains `isConversationRow` and two `.filter(…)` calls; `jarvis.ts`
imports the same predicate — it already imported from `./handler.js` (`:74`), so the direction of
that dependency was checked before choosing where the predicate lives, and no new file and no

### 6.2 The finding that outranks the rest: the invariant is not enforced

The predicate requires the sort key to carry no `#` after the chatId. This session wrote that as
though it rested on an existing repository invariant. **It does not.** Two producers can emit a
`chatId` containing `#`:

- **`safeDashboardChatId` returns an already-prefixed id verbatim** (**A137**). A send-route request
  body carrying `chatId: "dashboard:a#b"` is stored as `SK=CHAT#dashboard:a#b`.
- **The Paperclip dispatch chatId is never character-filtered** (**A138**):
  `paperclip:${issueId}`, with `issueId` supplied by an external system and only trimmed.

Such a conversation is **silently dropped** from all four readers — no error, no log, no count.
Nothing is pushed or deployed, so nothing live is affected today.

It was found because two independent reviewers contradicted each other about it and the
contradiction was re-derived rather than adjudicated (**P82/M73**). Note which way the danger ran:
the *reassuring* review was the wrong one.

**It is NOT patched, and the reason matters.** Both available fixes change something outside this
work item: sanitising at the write path means `sessions-repo.ts`, which the handoff puts out of
scope, and relaxing the predicate to a `#MSG#` blocklist weakens the release gate the owner defined
in decision 11 — the opportunistic patch **constraint 4** forbids. It also would not survive P3's
attachments, which add a second record type to the same key space. It is question 1 in section 8.

### 6.3 Two review findings that belong to WI-1.2, not here

Both WARN reviewers independently raised that filtering **after** a bounded read can under-report:
the cross-agent branch `Scan`s `Limit: 100` then slices 50, and the per-agent branch pages while
`items.length < 1000`. Today the table holds at most a handful of foreign rows per partition, so the
dilution is negligible. **Once WI-1.2 writes one record per message it is not**, and DynamoDB's
ascending sort order means a single busy conversation's `MSG#` rows sort immediately after their own
conversation row and can fill a page. Neither JSON route carries any truncation signal.

That is a real design consequence of the storage change, and it belongs to the specification of the
